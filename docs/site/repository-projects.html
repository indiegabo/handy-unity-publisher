Git-backed Unity Projects

Connect repository projects without turning them into second-class flows.

Repository-backed projects remain the canonical automation surface for HGP. The beta supports repository source settings, explicit access binding, build targets, publish destinations, and manual release execution from the desktop shell.

Before you create the project

  • Confirm the repository URL is stable and reachable from the host.
  • Connect a reusable repository credential or GitHub login if the repository is private.
  • Know which Unity version the repository expects before defining build targets.

Repository onboarding flow

  1. Open Projects and create a new project.
  2. Choose the repository-backed source mode.
  3. Paste the repository URL and let HGP detect the provider.
  4. Bind the project to the correct repository access method.
  5. Define build targets and any publish destinations the beta should run.
  6. Save the project and inspect the project detail surface before queuing work.

Manual checks and release dispatch

Instant checks

Use project-level inspection when you want to verify access and refresh remote information without waiting for scheduled polling.

Manual releases

Manual execution is the safest way to confirm a new repository project before you leave automation fully active.

Idle-safe operations

Idle posture blocks automatic polling intake, not the entire shell. Operator-driven inspection and release work remain available.

What to inspect after the first successful run

  • Build history shows the expected repository commit and target results.
  • Artifact inspection resolves the output files you actually need.
  • Runtime logs do not show repeated authentication or Unity resolution errors.
  • Publish destinations only bind to reusable credentials that are already healthy.
